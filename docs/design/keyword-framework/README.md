## 1. 本轮目标与范围

采用用户明确要求的顺序：**先搭建可扩展的关键词处理框架，再以`@预期`实现第一个业务模块，并在DSH插件管理页面看到整个调度过程的执行日志。**

框架第一批本身就要可验收：识别、配置、任务接纳、去重、取消、重启恢复、原生Jobs执行与管理页日志均跑通。用真实临时目录及仅测试装配的确定性处理器验证；该处理器不加入生产关键词注册表，不生成虚构交易材料。

第二批才接入`@预期`：当日原句整理、持久观察清单、后续交易日比对、人工确认。其他关键词暂不作为本轮业务交付；扩展能力用接口契约证明，不提前实现概念、模式、龙虎榜。

本目录是本轮实施的优先依据。`docs/design/card-processors/`保留为前一版多模块方案和语法细节的参考，**不再按旧第07份的八步骤实施**。

| 前一版内容 | 本轮调整 |
| --- | --- |
| 概念与预期一起作为首批 | 先交付框架，再只交付预期 |

## 5. 用户实际体验

1. 在卡片中写`@预期`，输入时仅显示识别提示。
2. 保存成功立即返回；后台登记任务，不阻塞继续写卡。
3. 在DSH插件管理页打开本插件详情，看到“关键词任务与执行日志”：排队、等待原因、尝试次数、执行阶段、结果或错误。
4. 每次实际执行关联一个原生job；Agent任务另有关联的独立执行会话。模型闲置不等于业务成功。
5. 预期原句整理后出现在观察清单；后续比对和人工确认分别留痕。
6. 关闭插件或模块暂停后续处理；重新开启先复核再恢复。删除关键词或卡片明确撤回对应观察，历史不删除。

## 6. 第一版明确的限制

- 单用户、单profile、单写者；本轮不实现多租户队列或分布式锁。
- 预期首版以文字为必要输入。图片可保留展示，但不宣称已读图；图片预期与模式分析后续另行接入。
- 自动回查必须有可核验业务日期的日线和交易日序列。缺数据能力时明确等待，不把实时行情冒充目标日。
- 管理页和原生Jobs为公开接口层只读核验，不等于当前运行宿主已完成接线。
- 原生job日志是有界、内存型；持久阶段日志来自业务记录，不承诺保存全部模型token或无限历史。

## 7. 审阅重点

优先审阅：框架是否保持业务无关；首个模块是否完整验证扩展方式；管理页是否包含“尚未启动模型”的等待阶段；暂停/撤回/重跑是否区分；历史数据不足时的回查行为是否清楚。具体实现顺序和每步出口以第04份为准。
