# 简单关键词入口与开放 Agent 工作流：设计调整

日期：2026-10-10。依据用户本轮明确的理念：保持简单，以复盘卡片为起点，一个关键词对应一个 Agent 工作流，工作流实现保持开放。

2026-10-11 澄清：代码编排属于第一版就具备的扩展能力，不能先把工作流限定为提示词，再等新需求出现重建框架。“简单”约束公共框架和接入负担，不限制工作流可以表达的业务。

本文修正既有设计的职责边界。01–04 中与本文冲突的强制六方法、双执行分支、通用业务观察机制不再作为第一批要求。本文是设计调整，现有源码和旧任务书尚未同步改造，不能直接按旧接口继续全部实现。

## 1. 是否符合预期

| 用户原则 | 现有设计 | 判断与调整 |
| --- | --- | --- |
| 从复盘卡片中的关键词开始 | 保存后通过写通知读取实际卡片正文，识别关键词 | 保留；输入提示不执行，保存成功才登记 |
| 一个关键词对应一个 Agent 工作流 | 关键词映射 ProcessorModule，模块内按stage选择agent或data | 部分符合；外部直接映射工作流，步骤和取数在工作流内组织 |
| 实现保持开放 | 自定义功能通常必须新增代码模块，实现六个方法并匹配固定schema/Skill | 统一执行契约从首版支持代码工作流；Skill/提示词作为该契约的一种实现 |
| 理念简单 | 公共层提前包含后续业务观察、业务锁、结果投递与双分支 | 收缩公共层；预期跟踪和确认留在预期工作流扩展里 |
| DSH管理页看到执行日志 | 持久任务日志加原生Jobs关联 | 保留；这是运行可观察性，不是业务流程编排 |

## 2. 建议采用的方式

采用“简单触发框架 + 开放工作流实现”。

可选的另外两种方式是：只映射到固定Skill，接入最少但不方便表达代码编排；保留当前六方法模块框架，可表达业务状态但对每个接入者都施加较重协议。推荐从第一版建立统一、可注册的工作流执行契约。代码工作流和Skill适配器使用同一接入面，不以提示词方式为公共框架的能力上限。

一条配置表达“识别这个关键词，启动这个工作流”。框架不配置工作流内部的extract/check等步骤，不要求每个工作流实现预期观察协议。

外部流程：保存卡片 → 识别关键词 → 查工作流映射 → 创建一次运行 → 启动Agent工作流 → 保存结果与日志。

### 2.1 与旧方案的实际区别

外部触发流程基本相同，旧方案也支持代码扩展和业务隔离，不应把它描述为完全不可扩展。变化在于接入协议和编排归属：

| 对比项 | 旧方案 | 调整后的方案 |
| --- | --- | --- |
| 新工作流接入 | 每个模块必须实现投影、准备、提交核验、结果校验、投递、来源协调六方法 | 注册一个实现，提供统一执行入口；默认生命周期由框架/适配器承接 |
| 执行步骤 | 注册表描述stage以及agent/data方式，公共层参与阶段协议 | 注册表绑定工作流，内部步骤由实现组织，框架调用整次执行 |
| 提示词/Skill | 依附模块及允许的stage/schema组合 | 是统一执行契约的一种适配实现，代码编排同样是正式接入方式 |
| 业务观察/回查 | 公共协议提前包含业务guard、后处理及观察请求 | 必要业务校验由工作流调用受控能力；通用运行服务不解释业务状态 |
| 生命周期、来源保护和日志 | 公共框架和模块回调配合完成 | 保障继续存在；默认通用行为不要求每个作者重复编写 |

统一执行入口不会自动消灭实现复杂度；改进是使工作流作者不用为无关能力写空方法。若执行入口内部仍强迫所有实现满足原六方法协议，就只是改名，没有完成这次职责调整。

## 3. 一个关键词、一个工作流的具体含义

### 3.1 公共业务模型固定为四个对象

高扩展性不扩大公共业务模型。框架只向使用者和工作流作者表达以下四个对象：

| 对象 | 简单定义 | 不应混入的含义 |
| --- | --- | --- |
| 复盘卡片 | 工作流的起点，包含用户保存的复盘内容 | 不是流程节点或任务容器 |
| 关键词 | 指向一个工作流的触发标记 | 不表达工作流步骤或执行方式 |
| 工作流 | 对卡片开展处理的一份可注册实现 | 不限定为一段提示词，也不要求作者实现一套公共业务观察协议 |
| 运行记录 | 某张卡片触发该工作流的一次执行及其状态、结果、日志 | 不等于工作流定义，也不等于宿主Agent会话 |

关系固定为：卡片命中关键词，关键词指向工作流，框架为该卡片启动工作流并保存运行记录。

关键词别名、输入版本、尝试编号、执行凭据、原生job和Agent会话关联是上述对象的属性或内部运行机制，不新增为公共业务对象。结果和日志归属于运行记录；存储时可以分文件，不因此增加业务模型。

`@预期`自己的观察条目、判断条件和确认记录由预期工作流定义与维护。其他工作流只需理解自己的业务，不依赖预期模型。业务扩展需要的新模型留在对应工作流实现中。

### 3.2 映射和运行规则

- 一个规范关键词只能对应一个工作流定义，重复绑定拒绝配置。
- 多个别名可以指向同一个定义，例如“预期”和“期待”都可由同一工作流处理。
- 同一张卡片多次出现同一关键词，只启动一次该工作流，输入包含整张卡片和全部命中位置。
- 一张卡片包含两个不同工作流的关键词，分别创建两次运行，互不把对方的成功当作自身成功。
- 同一个关键词出现在不同卡片，各自创建运行；“一个工作流定义”不等于所有卡片共享一个常驻Agent。
- 默认每次运行关联一个独立Agent执行会话。工作流内部是否多轮、分步骤或使用子Agent由实现决定；依赖的宿主能力必须实际核验，不以设计文字当作已支持。
- 初始材料必须包含这张卡片的来源身份、正文快照和命中信息。工作流可以读取明确授权的额外材料，卡片始终是追溯起点。

## 4. 模块划分固定为三个职责

| 模块 | 输入与输出 | 内部承担的保障 |
| --- | --- | --- |
| 关键词触发 | 保存后的卡片 → 对应工作流的启动请求 | 识别、关键词绑定、开关、来源核验和重复通知合并 |
| 工作流执行 | 启动请求 → 本次执行结果或失败 | 工作流注册/调用、授权运行上下文、宿主执行、并发、超时、取消和清理 |
| 运行管理与日志 | 执行过程 → 运行记录及DSH管理页 | 状态、结果、阶段日志、恢复记录及重新运行/取消入口 |

这是三个职责模块，不要求源码只用三个文件。模块之间的版本核验和落盘一致性是内部接口约束；不再引入业务“处理器层”“阶段层”“观察层”作为所有工作流必须理解的接入模型。

网络调用在短锁外；结束任务后清理资源再释放并发；私有提交凭据不展示到页面；提交时核对来源版本，旧输入结果不能覆盖当前结果。这些保障由模块内部承担，不变成工作流作者必选的生命周期方法。

框架不判断预期是否兑现、不决定次日取什么行情、不维护所有业务观察状态，也不统一规定每个工作流输出相同的业务字段。

## 5. 工作流实现如何保持开放

### 5.1 统一工作流接入契约

第一版先确定：工作流定义如何注册、框架如何调用一次执行、运行上下文提供什么能力、如何返回结果和失败。关键词绑定受信的工作流实现，不直接绑定一段只能发给模型的字符串。

对工作流作者的最小理解是“注册一个工作流，接收卡片运行上下文，返回结果”。扩展步骤、工具和业务规则写在该工作流内；共享执行能力由运行上下文提供。高扩展性体现在这一个入口可以承载不同实现，不能以扩展性为由增加更多必选业务对象或接口层次。

工作流可以取数、多轮调用Agent、使用工具、做条件判断、组织多个内部步骤和生成业务产物。新增步骤应在工作流实现里完成，既有能力范围内不改关键词解析、调度器或日志页面。新增宿主能力仍可能需要扩展受控服务，这不等于每新增关键词就重建框架。

不预先建设图形流程编辑器、节点DSL或另一套通用调度引擎；代码组合和已核验的宿主Agent能力先满足扩展。统一接口先落定，准确TypeScript签名随后同步到开发契约。

### 5.2 Skill / 提示词适配实现

适合整理文字、总结、分类等。工作流定义选择明确的Skill或提示词、模型配置、允许的工具和上下文。通用Agent适配器负责启动、等待明确结果和清理，作者无需编写生命周期模块。

新增这类关键词主要增加工作流定义和Skill/提示词，不要求修改scheduler，也不要求新增六方法TypeScript模块。Skill必须来自可核验的受信注册来源；配置不执行任意JavaScript或任意路径写入。

### 5.3 代码编排实现

适合需要先取数据、再多轮Agent处理、再写业务产物的流程。接入面建议只有一个必需的执行入口：接收框架提供的运行上下文，返回本次执行结果。

运行上下文提供：卡片快照、关键词命中、运行ID、取消信号、日志记录能力和经过授权的宿主工具能力。工作流可自由组织内部步骤。准确TypeScript签名在下一步公共契约修订时确定，本文不把伪代码当作现有可调用API。

这是首版扩展点，不是提示词不足时才增加的第二套入口。Skill适配器本身也通过该执行契约运行。执行入口接收完整工作流请求，不强制“一次运行只能调用模型一次”。

来源读取、权限和结果落盘继续通过受控服务；工作流的“开放”是实现自由，不是模型自行选择保存路径或绕过来源版本校验。

### 5.4 可选业务扩展

自定义输入投影、业务结果校验、受控结果落地及来源变化处理可以作为扩展能力，普通工作流使用默认行为。扩展由适配器承接，不全部变成必选方法。

如果工作流要改业务记录，仍需在实际业务写入处校验来源和业务记录版本，并确保幂等；不能因为简化接口而删除防止迟到结果覆盖人工修改的保护。旧commitGuard/afterCommit中的有效保障可在预期适配器内部复用。

## 6. 触发规则保持可解释

| 用户动作/系统事件 | 默认行为 |
| --- | --- |
| 正在输入关键词 | 只显示识别提示 |
| 首次保存带已启用关键词的卡片 | 创建运行并排队 |
| 相同正文再次保存 | 不重复运行；工作流定义或有效参数变化需单独记录 |
| 修改正文后保存 | 创建新输入版本；旧运行协作取消，迟到结果标旧版本 |
| 删除关键词/卡片 | 停止对应未结束运行，保留历史；具体业务撤回由该工作流负责 |
| 手动重新运行 | 以当前已保存输入创建新的运行记录，不抹掉旧日志 |
| 修改关键词映射/关闭工作流 | 后续按新配置执行；未结束旧运行取消或待复核；历史保留 |
| 重启插件 | 恢复已登记未结束运行，不自动重扫最近7日全部旧卡片 |
| 用户显式选择日期范围重扫 | 才登记范围内尚未处理的卡片，沿相同去重与额度 |
| 工作流写入附注/产物 | 默认不触发自己，框架只以用户正文作为初始输入 |

正文默认整卡参与输入指纹，第一版不要求每个工作流自行写projectInput。恢复时已经保存结果的运行不能再次启动Agent；被中断且无结果的运行明确标中断，重新执行必须生成可区分的尝试并计额度，不能假称接续了旧会话。

## 7. 生命周期和日志

框架只有“一次运行”的生命周期：排队、等待、运行、成功、失败、取消。等待用中文原因解释能力缺失、容量或额度。准备步骤记为日志；重试记为尝试记录。底层若需要preparing等内部状态，仍可以保留，但不要求工作流作者管理它们。

运行结束必须有明确结果或失败，不以Agent空闲、原生job结束代替业务成功。结果先保存为历史，再按来源版本决定是否仍是当前有效结果。完成后的日志/产物补交不能让成功任务倒退或重复启动Agent。

DSH页面的主要对象是工作流运行，显示：关键词、工作流名称、来源卡片、触发原因、运行状态、开始/结束时间、阶段日志、结果摘要、失败原因、原生job及Agent会话关联。关键词只是入口名称，不再把框架stage展示为用户必须理解的业务协议。

工作流通过统一日志能力报告“开始读取材料”“Agent开始整理”“结果已保存”等阶段；通用适配器记录默认阶段，因此简单Skill也能看到完整过程。第一版不承诺保存全部模型思考/token流。

## 8. 预期工作流的位置

`@预期`对应“预期整理与跟踪”工作流。该工作流自行完成提取原句、建立观察、后续取证和人工确认。它可以有多个内部步骤；框架仍只认识工作流及其每次运行。

次日回查是预期业务自己的后续触发规则，携带原卡片来源，再调用公共启动能力并沿用日志。框架首版需明确通用后续运行请求的登记、来源关联、取消和恢复边界，以及未具备执行条件时的可用性表达；预期实现决定交易日、证据和何时提出请求。不能把交易日窗口、预期确认、通用业务锁协议变成所有关键词的接入门槛，也不能等预期出现后再新增一套独立运行器。具体调度接口在公共契约修订时落定，本文不宣称已有可调用实现。

第一批用一个仅测试装配的普通Agent工作流验证：保存卡片、解析映射、独立执行、明确结果、管理页日志、取消与恢复。生产表保持空，第二批再注册预期。
